# Drift Atlas

A dependency-free static browser application for Sectors Without Number exports, with perspective-projected 3D cartography and Starfinder 2e travel tools.

## GitHub Pages hosting

The live site is published by the **Deploy Drift Atlas to GitHub Pages** workflow. Every push to `main` runs the simulation tests and deploys `dist/` after they pass. You can also run the workflow manually from the Actions tab. There is no server or build step, and all asset URLs are relative so repository subpaths work.

Repository administrators can enable hosting under **Settings → Pages → Build and deployment → Source → GitHub Actions**. The workflow uses GitHub's short-lived deployment credentials; no personal tokens or other secrets are needed in the repository.

Run `npm test` with Node.js 24 or later. For local use, run `python -m http.server 8000 --directory dist` and open `http://localhost:8000`.

### Moving your saved campaigns

Browser storage does not transfer between site addresses. On the old Drift Atlas site, open **Menu → Save / Load**, open each campaign you want to keep, and **Export current sector/cluster**. On the GitHub Pages site, use **Import sector** or **Import cluster** to load those JSON files. Cluster exports include member sectors, placement, connections, factions, and simulation progress. Separately saved campaigns must each be exported. Keep the JSON files as backups.

The public repository includes the application and bundled default sector. Your browser's imported campaigns and notes stay local and are not uploaded to GitHub. The earlier ChatGPT Sites deployment can remain available while you transfer saves.



Drag to orbit, shift-drag to pan, scroll/pinch to zoom. Arrow keys orbit, +/- zoom; system index supports keyboard selection. Mobile users can use System index to open the explorer, select a system, and use Details or Enter system from the selection card.

X and Y retain SWN coordinates. Missing Z is derived deterministically from entity ID. Heights and captain's notes are stored per-sector in the browser's campaign library and included in downloaded exports. No private notes are sent to a server. The bundled default sector, Aurelian Expanse, is part of the static site. Its 216 entity names use a Greco-Roman theme; IDs, coordinates, collections, hierarchy, survey attributes, tags, and hidden flags match the original generator export. Imported sectors keep their own names. Roma Aeterna is the original TL5 world and renders as an ecumenopolis. GM hidden-entity filtering is a view preference, not access control.

Travel profiles follow https://2e.aonsrd.com/rules/654-starship-travel-times and Plot Course follows https://2e.aonsrd.com/actions/94-plot-course. Campaign travel has two interstellar modes. Drift Lane follows the shortest connected path at 7 days per jump. The Vast draws a direct route but calculates dice from that same path: (jumps × 4)d6 days (1 jump = 4d6, 2 = 8d6, 3 = 12d6, 4 = 16d6). Both modes can be selected at any distance, and the calculated duration or dice count is automatic. Plot Course adjustments apply to the calculated base journey. Plot course or Roll travel time commits the course so it remains visible after closing the flight computer. Clear it from the course card. The lane-layer checkbox only controls background lane visibility. Selected lane segments remain highlighted even when the background layer is hidden. Local navigation uses individual planets, moons, stations, and facilities as endpoints in the current system, with a schematic route line. Dossier buttons set an object as departure or destination. The flight computer switches between local and interstellar travel without mixing endpoint lists. Local profiles include standard engines (1d6+2 days), Drift engines (1d6 days), satellite-from-orbit transfers (1 hour), launch/landing (1 hour), and point-to-point surface travel (1d4 hours). Satellite transfers require a parent world and its moon or orbital facility. Launch/landing and surface travel require locations on the same world; using that world twice represents different stages or surface sites. Hour-based legs use the base travel table without applying the long-journey Plot Course adjustments. Failure delay and critical-failure destination are determined by the GM. SWN world attributes remain unconverted narrative source data.

Select a star in the sector map or system index, then activate the same star again or use Enter system to open its schematic orbital view. A preselected or previously visited star still requires a new selection before entry. Objects can be selected in the canvas or Objects list; parent-child attachments from the export are retained, including moons and facilities. Return with Sector map or Escape. Stellar appearances use editable O/B/A/F/G/K/M colors; default classes are seeded visual assignments, not source measurements. Overrides are saved with campaign data. Orbital paths, sizes, and spacing are schematic because the export provides no orbital elements.

`dist/models.js` contains shared procedural 3D meshes for all facility types and shaded spherical terrain models for planets and moons. The orbital view, object-list thumbnails, and rotatable dossier viewer use the same model definitions. In the map, facilities have smaller visual footprints than moons and planets; model viewers and thumbnails use their own inspection scale. Planet surfaces use survey atmosphere and temperature; settlement density follows population, while technology controls urban materials and artificial lighting. Cold worlds gain ice and cooler tones; warm worlds lose ice and gain drier tones. Unknown population/technology do not invent city lights. The texture cache includes these traits so reimporting revised survey data updates the same world immediately. TL5 planets always render as ecumenopolises, including worlds with old saved surface overrides: continuous city districts, transport grids, and raised arcology towers replace the natural surface. Population controls activity and lighting, so uninhabited TL5 worlds remain visibly built but abandoned. Other inhabited planets render daylight-visible settlement foundations, blocks, and towers with population-scaled footprints and technology-dependent materials and heights; sparse outposts also get visible structures. The dossier provides an optional visual override for other planets which is saved locally and included in campaign JSON exports. Visual overrides do not change the source survey attributes.

The camera looks toward the grid from positive height at positive pitch. Depth increases away from the camera; positive Z is nearer in top view. Perspective scale, body occlusion, map picking, and grid picking share this distance convention through full rotations.

`dist/depth-render.js` draws sector stars and local objects in camera-depth order using their actual rendered silhouettes. Opaque surfaces hide objects behind them; station/gate openings and transparent atmospheres remain open. Fully hidden bodies do not draw labels, selection rings, or gate indicators and cannot intercept map clicks. Picking prefers the nearest visible solid surface before padded touch targets. Selection does not enlarge stellar cores. Planet and moon discs are opaque beneath their surface textures, and gas rings draw behind and in front of their own planet. Sprite reuse and cached map bounds keep large-map camera movement responsive.

The map network uses `_driftAtlas.lanes` when present (an array of undirected `[fromId, toId]` pairs). Otherwise the existing two-nearest-neighbor map links generate the network once on import. Search and camera movement never redefine jumps, and height edits preserve existing connections. Exports include the network for stable roundtrips. Disconnected endpoints have no measurable lane-jump count, so travel calculations are disabled with an explanation. Hidden objects are excluded from navigation when the GM visibility layer is off.

Each connected system has one bidirectional Drift gate for each adjacent lane. Gates are generated at the system boundary along the normalized sector-space vector to the neighboring system, including its Z elevation. The reciprocal gate points back toward the original system. Degenerate co-located systems use a repeatable, explicitly labeled schematic bearing. Gates have a distinct 3D aperture model, list entries, bearings/elevations, and a destination-system label. They can be selected as local departure/destination endpoints or used to plot the connected interstellar lane. Active lane courses mark the corresponding gates as entrance or exit. Hidden neighbors do not generate visible gates. Gates regenerate from the exported lane network and heights; they do not add fabricated source-survey entities to the JSON.

Click or tap empty map space, or a UI area outside location details, to clear the current location selection and hide its dossier. Selecting another location switches selection. Clicking inside a dossier, editing its fields, and dragging the map preserve selection. Deselecting a local object keeps the current system open and preserves plotted courses. Close buttons also clear selection.

## Saved maps

Menu → Save / Load provides a browser-local campaign library, grouped into Clusters and Sectors. Imports save automatically to IndexedDB, along with canonical lanes, generated heights, notes, stellar classes, and planet appearance overrides. The most recently opened sector or cluster is restored on startup before fetching the bundled default. Save current sector also writes an explicit snapshot; Open default sector switches back to Aurelian Expanse. Each library entry is identified by sector IDs/names and system IDs, so the renamed default and original example retain separate edits. Existing legacy default-sector overrides migrate on first load. Small synchronous edit backups cover a refresh during the autosave debounce. Sector writes and active selection commit atomically, and saves are serialized to avoid older writes replacing a newer active sector. A failed/quota-blocked save shows NOT SAVED and directs the user to export; it never claims success. Removal requires confirmation and only applies to inactive entries. Saves belong to the current browser/device and are not shared with other visitors; JSON export/import remains the portable backup.

## Sector clusters

Choose Menu → Manage Cluster Sectors. Add a new sector or select an existing sector to edit. Select a saved sector or import a single sector JSON, choose a reference grid and Top/Bottom/Left/Right, or drag any selected grid in the preview to a custom position. X/Y fields and keyboard arrows provide precise placement; mouse and touch dragging are supported. Grids retain the source rows/columns (or grow to encompass source coordinates). Directional presets use a two-unit gap and align centers perpendicular to the chosen direction; custom placements retain their exact X/Y translations. Overlapping placements are shown in red and cannot be added; drag to free space or change the offsets. Preview geometry stays fixed during a drag to prevent the grid from jumping under the pointer. Automatic links in custom mode choose the facing edges from the actual relative positions; explicit manual star pairs remain selected while dragging. Saving manager changes returns to the combined view, resets pan/zoom, and centers on the union of all remaining grid bounds. Cluster perspective depth scales with the combined extent to keep large maps stable. Each grid has a distinct border, color, and label; crowded star labels are suppressed without hiding stars or index entries.

Automatic mode connects one, two, or three pairs among the facing edge stars (nearest quarter of stars to the edge, at least three candidates where available), using 3D distance with distinct endpoints. Hidden stars are excluded from automatic selection. Each selected sector has independent connection controls for every other sector; check multiple peers to create multiple connections. Automatic counts (1–3) and manual star pairs are configured separately per peer. Connect nearby sectors enables links to grids within three map units, while manual target selection can connect any distance. Manual mode lets the user choose each pair from all stars of the selected and connected sector, including hidden stars when explicitly selected. Duplicate pairs are rejected. Cross-sector lanes are gold and are real edges of the canonical travel graph, with normal 7-day Drift Lane jumps, Vast dice, gate generation, and course highlighting. Search, zoom, and height edits never regenerate connections.

`dist/clusters.js` holds composition, placement, bridge selection, validation, and source extraction. `dist/cluster-ui.js` provides the manager and draggable top-down preview. `dist/cluster-edit.js` handles staged member changes, peer connection rules, nearby candidates, and deletion cleanup. `_driftAtlasCluster` version 1 contains a stable cluster ID/name, members (unique instance ID, X/Y offsets, full original sector document with campaign overrides), and explicit bridge pairs. Optional `connectionRules` records each sector pair’s automatic/manual mode and count. Explicit bridges are authoritative; automatic rules regenerate only when their member is moved or their settings are explicitly changed. Flattened view entities use namespaced IDs, so identical source IDs can coexist. Original references, coordinates, world tags, survey attributes, and unrecognized source fields stay in each member document. Internal lane networks and heights are prepared per original sector; visual seeds use original IDs so importing into a cluster preserves star and planet appearances. Snapshots sync notes, heights, stellar classes, model overrides, and internal lanes back into each member.

Save Cluster creates a new cluster from a standalone sector or updates the active cluster under its stable ID, with the editable cluster name. Save current sector uses a member selector in cluster mode and saves that member under its original sector identity without changing the active cluster. Cluster autosaves never overwrite standalone sector saves. Existing library entries without a type are treated as sectors; no IndexedDB migration or deletion is needed. Export current cluster writes portable JSON with all member data, placements, and links; Menu → Save / Load → Import cluster reopens it, restoring the sectors, placements, connections, and campaign edits. Both map import buttons use the existing JSON loader, which detects the file type automatically. Browser-local saves, blocked/quota storage behavior, and JSON backup limits still apply (15 MB per added sector, 100 MB for a cluster import, 3,000 combined map entities).

## Camera and panel interactions

A click/tap on empty space within a projected cluster grid centers the camera on that sector. Stars retain click priority and the existing two-step entry behavior. Grid picking follows the projected polygon through free rotation. Focus changes the camera pivot, so subsequent orbiting stays centered on the sector. Clicking/tapping empty space outside every sector grid clears focus and animates back to the full cluster center and overview zoom while preserving yaw, pitch, top-down mode, and any plotted course. Drags do not unfocus; tapping another grid focuses that sector. Reset view returns to the complete cluster with the default viewing angle. Returning from a system restores the previous focus, orientation, pan, and zoom.

System entry has a 460 ms zoom toward the selected star, followed by a 420 ms reveal of the orbital view. The render loop interpolates the camera and target star size. Escape, camera input, navigation, loading another map, and Reset can cancel an in-progress entry; no delayed callback can open a stale system afterward. Reduced-motion users enter directly. Flight-computer scope changes use immediate setup so local route endpoints are available in the same interaction.

Explorer and course panels dismiss on outside clicks/taps on desktop and mobile. Clicking within a panel or the button that opens it keeps it open, using the event's composed path even when controls rerender. A canvas drag rotates/pans without dismissing panels or selecting a grid. Outside course dismissal remembers the route inputs and preserves a committed course; map taps can also select a star or center a sector. System index, the local Objects button, and the / shortcut reopen the explorer.

## Managing existing cluster sectors

The manager stages all changes until Save cluster changes is pressed. Switching between sectors keeps a valid draft, allowing several additions, moves, connection edits, and deletions in one session. Cancel discards the whole manager draft. Reset sector edits discards only the current sector edits since it was selected. Invalid placement or duplicate star pairs block saving and switching; users can fix or reset the editor. Any existing grid can be selected and dragged directly with mouse/touch, or moved with offsets, arrow keys, and directional presets relative to another grid.

Automatic rules on a moved sector choose fresh facing-edge pairs for each enabled peer; manual rules retain their exact stars. Unrelated sector pairs and all internal lane networks are preserved. Older clusters without rule metadata open their existing bridges as manual connections to avoid guessing their original intent; choosing Automatic opts a peer into regeneration. Rules and endpoints survive cluster export/import and refresh. Source notes, heights, models, and raw survey data remain attached to stable member IDs.

Deleting a sector requires confirmation in the app and removes that member, all incident bridges, and its connection rules from the draft. Other sectors’ source data and standalone saves are unaffected. At least one sector must remain. Applying the new composition drops orphaned view overrides, rebuilds gates and route endpoints from the remaining graph, and keeps the cluster’s save identity. Browser save failures still report NOT SAVED and offer export; the previous successful stored snapshot remains available.


## Factions and territories

Menu opens Save / Load, Manage Cluster Sectors, and Factions. All map saving, loading, import, export, and the saved-map library live in Save / Load. The faction editor creates, renames, recolors, or deletes campaign factions, and assigns or clears ownership by orbital, system, or sector. Bulk assignments replace the ownership of every source orbital in the selected system or sector; an individual orbital can then be reassigned independently. Planets, moons, stations, facilities, belts, and other source locations participate through their parent hierarchy. A system with orbitals derives its controlling factions from those orbitals; an empty system uses its own assignment. Multiple owners make a system contested. Unassigned locations remain unclaimed.

The Factions checkbox on the map toolbar toggles the overlay; the menu and faction editor have no duplicate switch. Territories are bounded Voronoi regions on the sector plane; same-faction shared edges disappear, and contested regions carry alternating stripes for each controlling faction. A drift lane with shared faction ownership at both endpoints adds a corridor connecting their territories, including lanes between sectors. Corridors cover both the territory plane and the lane’s actual elevation. Only factions present at both ends extend across a lane; multiple shared factions stripe the corridor. Regions and corridors are composited as a union before outlining, avoiding internal borders at their joins. Colored rings identify ownership in the orbital view and controlling factions on sector stars. System and orbital dossiers, including nested locations in system survey details, provide faction dropdowns. Assigning a system replaces ownership for all its source orbitals; assigning an orbital changes just that location. Unclaimed clears ownership, contested systems are labeled, and changes autosave without closing the dossier. Territories follow the free camera projection, with the existing stellar colors preserved. The overlay is schematic political influence, not a physical volume or travel restriction.

Campaign faction definitions live in `_driftAtlas.factions` and ownership uses `factionId` in the existing per-entity campaign edits. UUID faction identities and definitions survive cluster composition, moves, sector extraction, autosave, refresh, and JSON export/import. Cluster member documents retain the catalog so a separately saved sector remains usable. The overlay preference is browser-local. Generator faction source data is retained independently.


Faction territory names appear in spaced uppercase text above stars, ownership rings, lanes, and system labels. Each connected territory component needs at least one fully controlled system; partial and contested-only ownership does not qualify. Layout uses a cached, camera-independent flat XY footprint, including ground lane corridors but excluding elevated surfaces and height curtains. Each name is centered at the area-weighted centroid of its connected territory; if a concave region places that point outside its footprint, the nearest inset interior point is used. Name span scales with the square root of territory area and is constrained by the territory’s overall width/height, not a local empty rectangle. There is no fixed pixel-size cap that makes large and small territories look alike. Each name has a fixed map-coordinate anchor that is projected as the camera rotates or pans: it never relocates to avoid stars or refits against the viewport. Font size follows the footprint and camera zoom/perspective, not the angle or height of the border; names smaller than 9 CSS pixels are hidden, and larger names retain their proportional scale. Separate qualifying enclaves can each receive a name. Text uses whichever of black or white has greater luminance contrast against the faction color, with the opposite-color outline. Names remain screen-facing, follow the Labels and Factions switches, and rebuild only when territory data, faction definitions, or fonts change.

Faction names smoothly fade out at close zoom and return when zooming out. Clusters use the zoom needed to frame one sector (including sector focus); standalone sectors fade out by 3× zoom. This only affects the names: faction borders and ownership rings remain visible. Hidden faction names no longer reserve space that suppresses system labels. Fade depends on camera zoom, so rotation does not change it.

## Faction turn simulation

**Menu → World simulation** adds a persistent SWN Revised faction-turn campaign to the current map. Review automatic intentions or queue manual orders, advance 1–100 configurable campaign turns with progress and stop controls, inspect faction sheets and 72 asset templates, follow a dice-and-events chronicle, and undo the entire latest advance. Purchases, upkeep, attacks, movement, expansion, and occupation affect the simulation; completed occupations update orbital ownership and the existing faction overlay. Controlled territory provides income based on population, technology, and facility type alongside SWN rating income; faction sheets show the breakdown, and Turn settings can select standard SWN income only. New faction setup populates all controlled orbitals with local assets, with larger capital packages. Existing campaigns can preview and populate their holdings from Overview without duplicating initialized garrisons. Profiles, assets, objectives, and relationships have GM controls. Simulation data travels with sector/cluster saves and JSON exports. No background turns run.
